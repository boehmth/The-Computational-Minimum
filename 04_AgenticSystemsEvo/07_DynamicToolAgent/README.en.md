# Chapter 7 · The Agent That Writes Its Own Tools

**When the model no longer just decides *which* tool it uses but *creates* the tool on the fly — what changes for Principle 3?**

Three miniatures, each a build-up of the same idea. The agent has **no hard-wired tools** any more. When it needs a tool that doesn't exist yet, it has the Python code generated by a second LLM call, validates it (AST whitelist + restricted builtins), executes it, and stores it in a registry — for future tasks. The second stage persists the generated tools to disk so that they survive across program runs. The third stage repairs the generated code itself when it breaks — via a specialised repair-LLM call.

By the end, after four questions the agent has four self-written tools in its registry, and it *no longer needs to regenerate them* the next time round. And a third miniature shows: **when the generated code is broken, the agent has it repaired by another LLM call** — the same LLM-guided-recovery idea from Chapter 3, but one level deeper.

> **Slide anchors in the deck:** Slides **45** (*"Where agents are heading — from tool users to tool makers: Fixed tools → Generated tools → Self-extending capability"*) and **46** (*"How this deck was made"* — the deck itself was built by Cline, the agent that generates tools mid-task). Chapter 7 is the smallest honest miniature of the middle stage: an agent that sits between "Fixed tools" (Chapters 1–6) and "Self-extending" (Devin, SWE-agent).

## 📏 Scaling as the red thread

Before we look at the miniatures in detail, one point is worth pulling out of the whole repo: **every extension so far has been a scaling of the same core idea.**

| Chapter | Tool palette | Who defines the tools? | What scales? |
|---|---|---|---|
| **1** | none | — | (only LLM, no tool) |
| **2** | 1 tool (`calculator`) | Developer, at design time | Principle: *split model / tool* |
| **2** (miniature 2) | 2 tools (`calculator` + `currency_converter`) | Developer, at design time | *Model picks from a set* |
| **3** | 2 tools, in a loop | Developer, at design time | *Chain tool calls* |
| **5** | any, over MCP | Foreign teams, at design time | *Tool catalogue grows externally* |
| **7 · M1/M2** | any, **generated at runtime** | The model, at runtime | *Catalogue grows internally, on demand* |
| **7 · M3** | ditto, **plus self-healing** | The model + a repair LLM | *Catalogue also gets repaired when broken* |

The arc reads: *if the calculator can be a tool, then anything can be a tool.* And *if a fixed set of tools works, a dynamic set can work.* And *if a runtime-generated tool can break, then the repair has to be at runtime too — with the same LLM pattern from Chapter 3.*

That is the actual value of Chapter 7: not the novelty of tool generation, but the recognition. **Chapter 7 is Chapter 3 with tools on both levels** — when calling *and* when creating.

## 📜 Historical context

The previous six chapters followed a clear arc: the model uses tools *you* wrote. Chapter 2 (`calculator`, `currency_converter`). Chapter 3 (loop that orchestrates the existing tools). Chapter 5 (foreign tools via MCP). Always: **tools are static, the loop is dynamic.**

From 2024 onwards a small but consequential shift began. In order:

- **March 2023** · Cai, Chen et al. — *"Large Language Models as Tool Makers"* (LATM, arXiv:2305.17126). A "tool maker" model writes reusable Python functions for a "tool user" agent. For the first time the tool library is built at runtime, not upfront.
- **Late 2023** · Voyager (Wang et al., NVIDIA/Caltech) demonstrates the same principle in Minecraft: an LLM agent that writes its own skill repertoire as it plays — and whose skill library after 200 hours of play contains more capabilities than the base agent ever had.
- **2024** · Code-interpreter-style systems become mainstream (OpenAI Advanced Data Analysis, Claude Code, Cursor agents). All share the same structure: the model writes code, the runner executes it, the result flows back into the next model turn.
- **2025** · State-of-the-art agents (Devin, SWE-agent, Claude Code) generate whole sub-programs at runtime, not just individual tool calls. The boundary between *"the model uses tools"* and *"the model writes software"* blurs.

This chapter shows the smallest honest version of that: **an agent whose tools are runtime-generated Python code**. No framework. ~450 lines including sandbox and persistence.

## 🔬 The three miniatures

### `src/01_dynamic_tool_agent.py` — the agent generates its tools at runtime

The core loop has three possible actions per turn, each as JSON:

```json
{"action": "generate_tool", "tool_name": "...",  "tool_description": "..."}
{"action": "call_tool",     "tool_name": "...",  "tool_args": {...}}
{"action": "final_answer",  "answer": "..."}
```

The flow for a typical task (*"Is 97 a prime number?"*):

1. **Turn 1** — The agent sees: registry is empty, there is no `is_prime`. It replies with `generate_tool` and provides a name (`is_prime`) and a precise description.
2. **In between** — The runner sends the name + description to a *second* LLM call (with an entirely separate system prompt for code generation), gets Python code back, checks it via the AST whitelist, compiles it in the sandbox namespace, and stores the function in the registry.
3. **Turn 2** — The agent now sees: `is_prime` is available. It replies with `call_tool`, `tool_args={"n": 97}`.
4. **In between** — The runner calls the freshly registered function, gets `True` back, appends the result to the history.
5. **Turn 3** — The agent replies with `final_answer`: *"Yes, 97 is a prime number."*

For the *next* question, if it needs an `is_prime`-like tool again, the agent skips steps 1–2 and goes straight to `call_tool` — the tool is already there.

### `src/02_dynamic_tool_agent_persisted.py` — the tools survive the process

Same logic, plus a registry that additionally writes every registered tool as a `.py` file under `src/generated_tools/`, with an `index.json` for metadata. At the next program start the registry loads every existing tool from disk — and validates each one **again** through the same AST whitelist. This matters deliberately: if someone edited the files between two runs by hand, the safety check still applies.

The result: after a few runs the agent has a small, growing library of tools it wrote itself. You can look at them in the `generated_tools/` folder and see: this is ordinary Python code. For example `is_prime.py`:

```python
def is_prime(n: int) -> bool:
    if not isinstance(n, int):
        raise ValueError("n must be an int")
    if n < 2:
        return False
    if n == 2:
        return True
    if n % 2 == 0:
        return False
    for i in range(3, int(math.sqrt(n)) + 1, 2):
        if n % i == 0:
            return False
    return True
```

No magic wrapper. No framework object. Just a function that the model wrote and that the runner reads back in at the next start.

### `src/03_dynamic_tool_agent_self_healing.py` — the agent repairs the broken code

In miniatures 1 and 2 the agent gives up if the generated code fails AST validation or throws an exception at call time. That is the pedagogically most honest version — it makes it visible that failures happen. But it is not what modern code-agents like Cline or Claude Code do. They do something more concrete: they **make one more LLM call** with a repair prompt that sees the broken code plus the error message, and get a corrected version back.

That's exactly what sits inside `SelfHealingToolRegistry`. An example transcript with `temperature=0.2`:

```
[Schritt 1] 'I need a median tool.' -> action=generate_tool
    -> generate tool code for 'median_of_list' ...
    -> Tool 'median_of_list' registered (correct on the first try).
[Schritt 2] -> action=call_tool
    -> Result of 'median_of_list({'values': [3, 1, 4, ...]})': 4.0

[Schritt 3] 'I need a mean tool for the second list.'
             -> action=generate_tool
    -> generate tool code for 'arithmetic_mean' ...
    -> Tool 'arithmetic_mean' registered.
[Schritt 4] -> action=call_tool  (with an empty list!)
    [repair] Runtime error in 'arithmetic_mean': ZeroDivisionError: division by zero
    [repair] Attempt 1/2 -- calling repair LLM...
    -> New code registered (now with `if not values: raise ValueError...`)
    -> Result: ValueError: 'arithmetic_mean' requires a non-empty list
```

Two things to notice:

1. **The retry policy lives in the registry, not in the agent loop.** The agent code from miniature 1 is reused unchanged. Just as in Chapter 3, where `03_retry_strategies.py` shows that a retry strategy is a swappable module — not a hardcoded `try/except` in the middle of the loop. Principle 3 in its clean form.
2. **The repair prompt is a *separate* system prompt.** Not the same LLM in the same role as on the first try, but a specialised debugger prompt that sees name, description, code and error message. That is precisely the "LLM-guided recovery" strategy from Chapter 3, here specialised to the case "broken generated code".

After the repair loop three outcomes are possible:

- **Success** — the repaired code passes validation, runs, returns a sensible value. The new code replaces the old one in the registry and is persisted to disk.
- **Give up** — after `max_repair_attempts` (default 2), the repair loop stops and re-raises the last exception. The agent loop then sees a normal `ToolCodeError` / runtime-error observation and has to decide what to do (usually: `final_answer` with "sorry, that didn't work").
- **`ValueError` passed through** — if the tool deliberately raises `ValueError` to reject its input (that's part of the contract — see `TOOL_GENERATOR_SYSTEM_PROMPT`), that does not count as a bug. The registry lets the exception through and the agent sees it as a normal error observation — just like a static tool's error in Chapter 3.

The line that makes the recursion tangible is in the script's docstring:

> *In Chapter 3 we compared four retry strategies: naive, exponential backoff, circuit breaker, LLM-guided recovery. Precisely the last strategy repeats itself here one level deeper: the LLM debugs its own generated code. That is not a new idea — it is the recursion of Chapter 3 onto Chapter 7.*

## 💡 Wow moment

The important moment is not the code generation itself — that has been standard repertoire of every capable model for a while. The important moment is the **recursion of Principle 3**.

> Principle 3 says: *everything around the model is your code.*

In Chapter 2 that meant: the parser is your code, the dispatcher is your code, the tool implementation is your code.

In Chapter 3 that meant: the loop is your code, the retry policy is your code, the stop condition is your code.

In this chapter one piece of *"your code"* is written by the model at runtime. **But the responsibility does not travel with it.** What you still have to write:

- The **sandbox** (`_validate_tool_ast`) — which language constructs are allowed, which are forbidden?
- The **namespace definition** (`ALLOWED_BUILTINS`, `ALLOWED_MODULES`) — what is the generated code allowed to see?
- The **persistence policy** — what gets written to disk, what deleted, what re-validated at start?
- The **error protocol** — what happens if the generated code fails validation, throws an exception, or returns nonsense?

Precisely these four responsibilities are the reason we start with a *narrow* sandbox (only `math`, `re`, `statistics`, `datetime`; no imports, no `open`, no `eval`). They are not pretty, but they are the price for being able to trust the generated code while it runs inside the same Python process as the agent.

The chapter's script says so plainly in its own docstring:

> *Executing dynamically generated code is fundamentally risky. The validation here (AST whitelist + restricted builtins) is a didactic approximation, NOT a substitute for real sandboxing (e.g. subprocess with resource limits, WASM sandbox, RestrictedPython, etc.).*

That is Principle 3 in its hardest form. The framework that would take this off your hands does not exist — or rather: the frameworks that *try* (LangChain's `PythonREPLTool`, `LlamaIndex`'s code interpreter, Anthropic's `computer_use`) only hide the policy, they do not make it safe.

## ⚠️ Security — what this miniature deliberately does *not* do

To remind ourselves, briefly and honestly:

- **No process isolation.** The generated code runs in the same Python interpreter as the runner. Escaping the AST whitelist would be enough to take over the agent process.
- **No resource limits.** A generated `while True: pass` will hang the agent. No timeout, no CPU cap.
- **No network protection** beyond the name blacklist. We rely on `socket`, `urllib`, `requests` being in `FORBIDDEN_NAMES` — that is banning-by-name, not banning-by-capability. Sophisticated generated code could go around it.
- **No formal verification.** We check the *shape* of the code (AST), not its *semantics*. A syntactically harmless `for i in range(10**12)` passes the whitelist and still bricks the process.

If you want to use this pattern in production, replace `compile_tool()` with a real isolation mechanism:

- **Subprocess** with `resource.setrlimit` (CPU time, memory, file descriptors) and JSON I/O over stdin/stdout — the simplest honest answer.
- **`RestrictedPython`** (Zope ecosystem) with the same module whitelists — more library, less bespoke code.
- **WASM sandbox** (Wasmer, Wasmtime) with a Python-to-WASM compiler like Pyodide — a real process isolate with memory bounds.
- **Container per call** (Firecracker, gVisor) — the enterprise answer, with millisecond cold starts.

The didactic version here exists so that you can see *which* questions a sandbox design has to answer at all. Once you see them, choosing between the four options above becomes a sober cost/security calculation instead of a "how hard can it be" gut feeling.

## 🧭 Where this chapter sits in the arc

The historical arc of the first six chapters was:

> Chapter 1: the model replies. → But the answer is wrong.
> Chapter 2: give it a tool. → But the tools are static.
> Chapter 3: build a loop. → But the loop costs tokens.
> Chapter 4: some models iterate internally. → But they do not replace the loop.
> Chapter 5: standardise the tool interface. → But the tools still come from humans.
> Chapter 6: the verdict — not everything is an agent.

**Chapter 7 asks: what if the tools no longer have to come from humans either?**

The chapter's answer is two-fold:

1. **Yes, that works** — the model can write its own tools, and the registry grows with every task.
2. **But the price shifts downward** — every line that used to validate a human-written tool (code review, tests, type checker) now has to be replaced with sandbox policy. And the sandbox is stricter than any code review could ever be, because it has to decide over *arbitrary unknown code*.

That is the state of the art in summer 2026. Systems like Devin, SWE-agent, Claude Code are elaborations of exactly this pattern — with better sandboxes, with real tooling (git, filesystem, browser), with multiple co-operating agent roles. But the core loop is this one.

Once you have understood this loop — the three actions, the registry, the sandbox — you have the conceptual tool to analyse any modern code-agent system. The rest is engineering.
